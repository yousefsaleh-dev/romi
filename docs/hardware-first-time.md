# ROMI: أول مرة تستخدم ESP32 — تبدأ منين؟

الملف ده لمطور ويب بيستلم الهاردوير لأول مرة. السيناريو الأساسي: البورد + مايك + أمبليفاير + سماعة يعملوا الاستقبال من زرار فعلي، بدون كمبيوتر أثناء التشغيل. لو قطع الصوت مش موجودة، الموبايل يبقى جهاز الصوت والبورد تفضل مسؤولة عن الباب.

الكود موجود ويتبني. **الهاردوير نفسه لسه غير مختبر**؛ مفيش ESP32 فعلية في بيئة التطوير. الموقع شغال على [romi-deci.vercel.app](https://romi-deci.vercel.app)، ونجحت سبع مجموعات للاختبار الكامل بعد تحديث مفتاح Gemini وإصلاح SQL رقم 0007: إصدار جلسة حقيقية وصوت Gemini وبروتوكول الحجز والباب. التفاصيل في [نتائج اختبار السيرفر](deployment-device-tests.md). ده لا يثبت قطع الصوت أو حركة السيرفو على البورد نفسها.

## 1. يعني إيه «القائمة»؟

أنا ضفت ملف اسمه `firmware/esp32-romi/romi.ps1`. ده برنامج صغير يشتغل على Windows من PowerShell لتجهيز البورد. مش صفحة في ROMI، ومش قائمة تظهر على ESP32، ومش extension لازم تبحث عنها.

افتح المشروع في VS Code → Terminal → New Terminal → اختار PowerShell. لو الـterminal داخل مجلد المشروع اللي فيه `package.json`، اكتب:

```powershell
.\firmware\esp32-romi\romi.ps1
```

على مسار جهاز التطوير الحالي يمكنك فتح PowerShell ثم:

```powershell
cd "D:\Ashbal Masr\ROMI"
.\firmware\esp32-romi\romi.ps1
```

لو عملت clone في مكان مختلف، استخدم مسار المجلد الجديد في `cd`.

الأمر يطبع هذه القائمة **في نفس شاشة الـterminal**:

```text
ROMI ESP32 launcher
1 prepare  : install/cache tools and compile modes before the event
2 WiFi     : change WiFi only; server settings are already included
3 doctor   : inspect tools, settings and USB ports
4 test     : flash offline bench mode and open logs (O/C/T/S)
5 flash    : flash standalone voice + door (mic/amplifier required)
6 monitor  : open live logs
7 audio test: flash offline mic/speaker diagnostics (M/A)
8 phone fallback: flash door controller; phone provides voice
Choose 1-8:
```

عند `Choose 1-8` اكتب رقمًا، مثل `1`، واضغط Enter. الخطوة تنتهي ثم البرنامج يقفل؛ لما أقول «افتح القائمة تاني» معناها شغّل نفس أمر `romi.ps1` مرة أخرى.

| الرقم | معناه بالعامية |
| --- | --- |
| 1 | نزّل أدوات البورد وجهّز الكود؛ اعمله قبل المسابقة |
| 2 | غير اسم الواي فاي وكلمة السر فقط؛ الرابط والتوكن والشهادة جاهزين |
| 3 | شوف هل الكمبيوتر شايف البورد وهل الأدوات موجودة |
| 4 | اختبر السيرفو والزرار والـLEDs بدون سيرفر |
| 5 | اكتب برنامج الاستقبال بالصوت على البورد |
| 6 | افتح شاشة رسائل البورد عشان تشوف الأعطال |
| 7 | اختبر المايك والسماعة والسيرفو بدون سيرفر |
| 8 | اكتب برنامج الباب فقط؛ الموبايل يتولى الصوت |

لو Windows قال إن تشغيل scripts ممنوع، نفذ في نفس النافذة:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
```

ثم أعد أمر فتح القائمة. اختيار 1 يحتاج الإنترنت. لو Python غير موجود، ثبّت Python 3.11 أو أحدث مع Add Python to PATH، وافتح terminal جديدًا. لا تحتاج Arduino IDE أو كتابة C++ لتشغيل السيناريوهات الحالية.

## 2. التوكن بين Vercel والبورد

أيوه، فيه توكن مشترك اسمه **ROMI_DEVICE_TOKEN**.

1. على Vercel: Project → Settings → Environment Variables، لازم المتغير ده يكون موجودًا.
2. نفس قيمته موجود بالفعل في `include/romi_secrets.h`، ويطابق `.env.local` للاختبارات. اختيار 2 يغير الواي فاي فقط؛ تغيير التوكن لاحقًا يتم بتعديل header أو `romi.ps1 configure` ثم flash.
3. بعد تغيير env على Vercel اعمل redeploy. بعد تغيير إعدادات البورد أعد رفع البرنامج.

البورد تبعته تلقائيًا في `Authorization: Bearer ...`. اختلاف القيمة يرجع HTTP 401. ما تعملش قيمة جديدة على البورد وحدها. **GEMINI_API_KEY وSUPABASE_SECRET_KEY يفضلوا على السيرفر؛ لا تدخلهم في إعدادات البورد.** لكل ضغطة تبدأ محادثة، البورد تطلب Gemini token مؤقت من API وتحفظه في RAM فقط. رابط السيرفر والتوكن والشهادة موجودون بالفعل في نسخة GitHub الحالية؛ يوم المسابقة أدخل الواي فاي فقط عند أول flash.

بعد النشر، اختبار خارجي أولي من الكمبيوتر:

```powershell
$env:ROMI_TEST_BASE_URL = "https://romi-deci.vercel.app"
pnpm smoke:device:external
```

تأكد أن `.env.local` فيه نفس device token. الاختبار الافتراضي يراجع authentication ورفض الطلبات غير الصحيحة؛ **لا يثبت دورة الحجز والباب كاملة**. للاختبار الكامل ونتيجته الحالية اقرأ [اختبارات السيرفر المنشور](deployment-device-tests.md). لا تجعل Vercel Deployment Protection تمنع طلبات الجهاز خلف صفحة login.

## 3. لو معاك قطع الصوت — التشغيل المستقل

جهز البورد ESP32 DevKit V1 / ESP-WROOM-32، المايك INMP441، الأمبليفاير MAX98357A، السماعة، السيرفو، الزرار والـLEDs. لو نوع القطع مختلف، راجع التوافق بدل توصيلها كأنها نفس النوع.

1. **وصل الأسلاك** حسب [جدول التوصيلات](../firmware/esp32-romi/STANDALONE.md#1-القطع-والتوصيلات). كل GND مشترك. المايك 3.3V؛ السيرفو والأمبليفاير 5V خارجي؛ البورد USB. لا توصل موجب الـ5V الخارجي إلى بورد متغذية USB. السماعة بين طرفي الأمبليفاير، وسالبها ليس GND.
2. **وصل USB البورد بالكمبيوتر** بكابل بيانات مناسب لمنفذها. كابل الشحن فقط لن يرفع برنامجًا. ابدأ والسيرفو منفصل عن ميكانيزم الباب.
3. **اختار 7**. الأداة ترفع اختبار القطع وتفتح الرسائل. اكتب `A` لسماع نغمة، اتكلم ثم `M` لمشاهدة قياس المايك، و`T` لتحريك السيرفو. Ctrl+C يقفل شاشة الرسائل.
4. **إعدادات السيرفر جاهزة بالفعل** في `include/romi_secrets.h`: رابط `https://romi-deci.vercel.app`، نفس device token الذي نجح اختباره، وشهادة HTTPS موثوقة. لا تحتاج اختيار 2 قبل أول رفع. عند اختيار 5 لأول مرة ستظهر تلقائيًا خانتان فقط: اسم Wi-Fi 2.4 GHz وكلمة السر؛ اكتب بيانات شبكة المسابقة أو hotspot المتاح وقتها. اختيار 2 تستخدمه فقط لتغيير الواي فاي لاحقًا، وبعده أعد الرفع. كلمة السر مخفية أثناء الكتابة.

5. **اختار 5**. الكمبيوتر يحوّل الكود الموجود لبرنامج، ثم يكتبه في ذاكرة ESP32 عبر USB. ده معنى upload/flash. انتظر SUCCESS، ولا تفصل الكابل أثناء الكتابة. لو توقف عند Connecting امسك زر BOOT الصغير على البورد واتركه عند بدء الكتابة. BOOT غير زرار استقبال الزائر على GPIO33.
6. **اختار 6** لمشاهدة الرسائل. انتظر Wi-Fi وNTP. اضغط زرار الزائر: البورد تطلب جلسة وتبدأ التحية بنفسها، وتسمع وترد. الضغطة التالية تلغي المحادثة. السيرفو يتحرك فقط لأمر مقبول من السيرفر، وليس لأنك ضغطت الزرار.
7. **اختبر بدون الكمبيوتر**: اقفل الرسائل، افصل كابل البورد عن الكمبيوتر ووصل USB بشاحن أو power bank. خلي مصدر 5V الخارجي موصولًا. البرنامج محفوظ في البورد؛ بعد إعادة التشغيل ستتصل بالواي فاي بنفس الإعدادات. جرّب الزرار تاني.

الكمبيوتر مطلوب لكتابة البرنامج وتشخيصه، وليس للتشغيل اليومي. إبقاؤه موصولًا أثناء الاختبار عادي؛ فصله يثبت الاستقلال. الكهرباء الخارجية ما زالت مطلوبة للسيرفو والأمبليفاير. الإنترنت والسيرفر وGemini مطلوبة للمحادثة.

## 4. أسوأ حالة: لا يوجد مايك أو سماعة أو أمبليفاير

**البديل العملي هو الموبايل، وليس الـPC الذي لا يحتوي على مايك.** صوت الموبايل يتعامل مع Gemini، والبورد تنفذ أوامر الباب من السيرفر.

```text
الزائر يتكلم مع الموبايل
→ ROMI API تتحقق من الحجز
→ ESP32 تستقبل أمر الباب
→ السيرفو يتحرك
→ ESP32 تبعت ACK
→ الموبايل ينتظر نتيجة الباب
```

1. وصل السيرفو والزرار والـLEDs؛ لا تحتاج توصيل قطع صوت ناقصة.
2. وصل USB البورد بالكمبيوتر. اختار 4 لاختبار السيرفو، ثم Ctrl+C.
3. رابط Vercel والتوكن والشهادة جاهزين. أول اختيار 8 يسألك تلقائيًا عن اسم الواي فاي وكلمة السر فقط.
4. **اختار 8** لرفع برنامج الباب فقط. انتظر SUCCESS. اختيار 6 يعرض رسائل الاتصال والأوامر.
5. على موبايل افتح موقعك المنشور HTTPS وسجل دخول admin، ثم افتح **`/dashboard/kiosk`**.
6. أدخل نفس device token في الصفحة، اسمح باستخدام الميكروفون، واضغط **ابدأ الاستقبال**. خليك على الصفحة وارفع صوت الموبايل لمستوى مناسب.
7. تحدث مع ROMI وجرّب حجزًا مقبولًا داخل نافذة الدخول. الموبايل لا يحرّك السيرفو مباشرة ولا يرسل ACK بدل البورد؛ البورد مسؤولة عن الأمر والنتيجة.
8. بعد الاختبار يمكنك تغذية البورد بشاحن USB؛ الموبايل يظل جزءًا من النظام في هذا البديل.

**حدود البديل:** بداية/نهاية المحادثة من شاشة الموبايل؛ GPIO33 لا يبدأ متصفح الموبايل بالكود الحالي. بعد refresh ستحتاج إدخال device token مجددًا لأنه محفوظ في RAM فقط. `/dashboard/simulation` للمحاكاة ولا يصدر أمر باب حقيقي. بدون مايك أو موبايل/جهاز صوت آخر، لا يمكن للنظام سماع الزائر. لا يوجد Bluetooth audio fallback.

لو الموبايل أيضًا غير موجود والـPC ليس به مايك، يمكن عرض dashboard والـservo باختبار 4 و`T` فقط؛ هذا عرض حركة يدوي، **ليس محادثة صوتية أو تحقق حجز يفتح الباب**. لو الإنترنت كله غائب، اختبارات القطع المحلية تعمل لكن Gemini وAPI لا يعملان offline.

## 5. ماذا تعني أسماء الأوضاع؟

اختيار القائمة يكفي؛ لا تحتاج حفظ الأسماء. هي أسماء إعدادات لنفس المشروع:

| الاسم | الاستخدام |
| --- | --- |
| full، اختيار 5 | صوت على البورد + باب؛ عرض هاكاثون بدون حساس |
| demo، اختيار 8 | باب على البورد + صوت الموبايل؛ عرض هاكاثون بدون حساس |
| audio-bench، اختيار 7 | اختبار قطع الصوت والسيرفو بدون شبكة |
| bench، اختيار 4 | اختبار السيرفو/الزرار/LEDs بدون شبكة |
| safe / full-safe | لا يقر نجاح الباب بدون حساس حقيقي؛ ليست الاختيارات المناسبة لعرضنا بلا حساس |

في اختياري 5 و8، نجاح الباب مفترض بعد وقت حركة السيرفو ويظهر `[DEMO]` في الرسائل. `servo.write()` ليس دليلًا على فتح باب فعلي. Production يحتاج تنفيذ حساس في `doorOpenFeedback()`.

## 6. لو حاجة وقفت

راجع [دليل الأعطال](../firmware/esp32-romi/HACKATHON.md#7-دليل-الأعطال-السريع): كابل بيانات، تعريف USB، منفذ مشغول، زر BOOT، كهرباء السيرفو، واي فاي 2.4GHz، شهادة HTTPS، HTTP 401 وVercel logs. تعديل pins/زوايا/مستوى الصوت في ملف واحد `include/romi_config.h` ثم إعادة الرفع.

قائمة الملفات ونتائج البناء وما يحتاج hardware فعلي موجودة في [سجل التحقق](../firmware/esp32-romi/VERIFICATION.md). نجاح build/اختبار Gemini من الكمبيوتر لا يثبت الأسلاك أو I2S أو استقرار ذاكرة ESP32 على قطع المسابقة.
